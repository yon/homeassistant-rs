# Engineering Principles

**Core principles that guide all engineering decisions in this project.**

---

## Principle 1: Correctness Over Cleverness

Write code that is obviously correct rather than code that is cleverly optimized. Clever code is hard to review, hard to debug, and hard to maintain.

- Prefer explicit over implicit
- Prefer readable over terse
- Prefer simple over complex
- If you must be clever, document why extensively

## Principle 2: Fail Fast, Fail Loud

Errors should be caught as early as possible and reported as clearly as possible.

- Validate inputs at the boundary
- Use strong types to make invalid states unrepresentable
- Return meaningful error messages with context
- Never silently swallow errors
- Prefer `Result<T, E>` over panics; prefer panics over silent corruption

## Principle 3: Test-Driven Development (TDD)

Write tests before implementation. Tests are a specification, not an afterthought.

1. **Red** — write a failing test that describes the desired behavior
2. **Green** — write the minimum code to make the test pass
3. **Refactor** — clean up while keeping tests green

Benefits:
- Forces you to think about the API before implementing it
- Ensures every behavior has a test
- Prevents gold-plating (writing code nobody asked for)

## Principle 4: Single Responsibility

Every module, struct, function, and crate should have one reason to change.

- If a function does two things, split it into two functions
- If a struct has two concerns, split it into two structs
- If a crate serves two purposes, consider splitting it
- Name things by what they ARE, not what they DO right now

## Principle 5: Dependency Inversion

Depend on abstractions, not concretions.

- High-level crates should not depend on low-level crates directly
- Both should depend on traits (abstractions)
- Use trait objects or generics to decouple components
- This enables testing with mocks and future flexibility

## Principle 6: Minimal Public API Surface

Expose the minimum necessary interface. Everything else is `pub(crate)` or private.

- Every `pub` item is a commitment to maintain
- Once public, removing it is a breaking change
- Start private, promote to public only when needed
- Document every public item

## Principle 7: No Broken Windows

Fix problems when you see them. Do not leave TODO comments without tracking.

- If you see a bug, fix it or file an issue
- If you see a warning, fix it or document why it is acceptable
- If you see dead code, remove it
- If you see a missing test, write it
- TODOs must have an associated issue number: `// TODO(#123): description`

## Principle 8: Incremental Progress

Make small, focused changes that are easy to review and easy to revert.

- Each commit should do one thing
- Each PR should address one concern
- Prefer many small PRs over one large PR
- If a change gets large, split it into a chain of smaller changes

## Principle 9: Observability by Design

Code should be observable in production from day one.

- Add structured logging at significant decision points
- Use tracing spans for operations that cross boundaries
- Emit metrics for things you will want to alert on
- Include correlation IDs for request tracing

## Principle 10: Secure by Default

Security is not a feature — it is a property of the entire system.

- Never trust external input (validate, sanitize, escape)
- Use the type system to enforce security invariants
- Secrets never appear in logs, errors, or debug output
- Dependencies are audited regularly (`make audit`)
- See `security-practices.md` for detailed guidance

## Principle 11: Documentation as Code

Documentation lives next to the code it describes and is verified with the code.

- Public APIs have doc comments with examples
- Complex algorithms have inline explanations
- Architecture decisions are recorded in ADRs
- README files are kept current (but never auto-generated by AI without request)

## Principle 12: Optimize for the Reader

Code is read far more often than it is written. Optimize for the reader.

- Use descriptive names (even if they are longer)
- Group related items together
- Use consistent patterns throughout the codebase
- Add comments for the "why", not the "what"
- Follow project conventions even if you personally prefer something else
